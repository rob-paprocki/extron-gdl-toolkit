# Extron `.gdl` — format and programmatic authoring

Notes from reverse-engineering Extron GUI Designer **1.28.0.7** project files,
verified end to end: machine-written `.gdl` files open in GUI Designer, survive
structural edits, and **build successfully**.

Everything here was derived from the files in `fixtures/gdl/`, GUI Designer's own
snapshot renders, and the installed assemblies. Nothing came from Extron
documentation, so treat version 1.28.0.7 as the tested boundary.

---

## 1. Container

A `.gdl` is a **ZIP whose 4-byte record signatures read `KP` instead of `PK`**
(local header, central directory, EOCD, data descriptor). Swap those two bytes
back and any standard ZIP tool opens it. Two members:

| Member | What it is |
|---|---|
| `ProjectGCP` | .NET `BinaryFormatter` graph of `Extron.GUICPro.PBProject`. **This is what GUI Designer opens and edits.** The embedded font binaries live here too. |
| `<project_name>.tgz4` | A plain ZIP (despite the name) holding the *built* panel payload: `layout.json` + `N.png`. Regenerated by Build; the panel's firmware reads this, though no load onto a touch panel is recorded here. |

Editing only `ProjectGCP` is enough. The payload goes stale and GUI Designer
rebuilds it.

**Only the records' signatures are swapped.** A member's compressed data can
hold the same four bytes by chance - the Turbulence huddle's 725
(`tests/data/design-panels-turbulence`) holds `KP 05 06` 50 MB into its
`ProjectGCP`, and a later version of the huddle built on the 1525 a `KP 03 04`
37 MB into its own - so swapping every occurrence in
the file damages that data, and reads as a wrong CRC-32 on a file GUI Designer
wrote whole. `gdl.container` finds the records as a ZIP reader does, from the
end of central directory, and swaps those alone, reading and writing.

## 2. What Build actually does

Measured by diffing a project before and after a build:

1. **Rasterizes** every control and every button state to a PNG sized to the
   control's exact rect, and writes them as `N.png`.
2. **Deduplicates by appearance.** One asset backs many controls (a single
   asset served 24 controls in the test project). **Text is not part of the
   raster** — two labels with different captions were assigned the *same*
   asset. `layout.json` carries them and the panel is expected to draw them
   live; nothing here observed a panel doing it (below).
3. **Assigns `TLPImageID`.** Authored controls carry `-1`; Build fills them in.
4. **Regenerates `layout.json`** from the authoring model.
5. **Auto-creates popup page references for every modal popup on every page.**
   A page authored with none came back with one per modal popup. Do not author
   these — the app manages them.
6. Bumps `VersionInfo` (one increment per save/build), updates `RevisionDate`,
   sets `BuildStatus=Done`, and renames the payload member to the file name
   lowercased with underscores — building `testB.gdl` produces a member named
   `testb.tgz4`.

**`Project > Verify` (Ctrl+B) is NOT this.** It validates and reports
"Build Complete - 0 error(s), 0 warning(s)", which reads exactly like a build,
but produces no payload - and saving after it writes a `.gdl` containing only
`ProjectGCP`, the stale payload dropped. The build above is
**File > Save and Build (Ctrl+Shift+B)**.

`PBProject.BuildProject()` is the method that does the work, and `BuildManager`
has a public `(PBProject)` constructor, but calling it outside the running
application throws `NullReferenceException` - in an interactive session too. The
build is not reachable headlessly; drive the UI instead
(`docs/from-scratch.md` section 7).

The practical consequence: **an authoring tool never makes artwork.** It sets
semantic properties (border, fill, icon, corner radius) and Build makes pixels.

**A point is the same number of pixels on every panel.** `layout.json` exports
only a font's `PointSize`, and live captions leave no pixels in the file, so
`tests/type_probe.py` bakes them instead: a button with `flattenTextField` true
has Build draw its caption into its artwork, from each state's **`ftextField`**
(not `textField` - a clone carries the donor's, `'               Preset 1'` on
the Afterburn seeds). "HHHH" at 14, 18, 24, 30 and 36 pt measured a cap height
of 13, 17, 23, 29 and 34 px on the TLP Pro 1035T (149 DPI), 835M (188.68),
1535M (127.7), 300M (164.83) and 1230WTG (166) alike - GUI Designer's own
1.375 px per point, whatever the panel's DPI. So 14 pt captions are 2.2 mm tall
on a 1035, 1.8 mm on an 835 and 1.1 mm on a 535. The limit: this is Build's
rasterizer; a panel is expected to draw live captions itself, which was not
measured.

## 3. Reading and writing `ProjectGCP`

Use **32-bit Windows PowerShell 5.1** —
`C:\Windows\SysWOW64\WindowsPowerShell\v1.0\powershell.exe`. Two reasons:
.NET Framework still has `BinaryFormatter` (removed in modern .NET), and
Extron's assemblies are x86, so a 64-bit host fails with "incorrect format".

Preload every DLL plus `GUI Designer.exe` from
`C:\Program Files (x86)\Extron\GUI Designer` into a hashtable and serve them
from an `AssemblyResolve` handler. Calling `LoadFrom` *inside* the handler
recurses until the stack overflows.

Re-serializing an untouched project is **not** byte-identical to the original:
it differs by **5,900 bytes** on the `_alt` fixture. But it is *stable* from the
first pass onward - pass1 vs pass2 and pass2 vs pass3 are both **zero**
differing bytes.

The difference is **every `TLPImageID` being reset to -1**: 654 of 654 controls, where the
original had 624 assigned and 30 unassigned. A save through the bridge
therefore invalidates all artwork assignments and correctly flips
`BuildStatus` to `Needed`. GUI Designer's own Save-and-Build restores exactly
the original 624/30 split.

This is harmless - Build reassigns everything - but it means a bridge-saved
`.gdl` always needs rebuilding, and it is why the byte comparison fails. Use
**pass1 vs pass2** as the regression test, or compare semantics.

`GdlProject.ps1` wraps all of this.

## 4. Clone, never construct

`PBPage(PBProject)`, `PBPopupPage(...)` and friends throw
`NullReferenceException` headless — they reach for `FormMain`, the toolbox
service and the undo engine. Property setters fail the same way, and are worse
than useless because they **write the backing field first and then throw while
notifying**, so a failed set looks like it worked.

Instead: deep-clone an existing object through `BinaryFormatter` and write its
backing fields by reflection.

This works because `ParentProject`, `Site`, `DesignView` and `PBSystem` are
`[NonSerialized]` — the stored graph is a pure data tree with no upward links,
so a page clones standalone (~107 KB, not the whole multi-MB project).
Collections are plain `List<T>` with ordinary `Add`/`Remove`.

Backing fields worth knowing:

| Field | On | Notes |
|---|---|---|
| `idField` | `PBControlBase` | UInt64, editor handle, unique **within its page** |
| `userIdField` | `PBControlBase` | UInt16 — this is the **ID** Extron shows and the control program addresses |
| `nameField`, `textField` | | |
| `leftField` `topField` `widthField` `heightField` | `PBDrawObject` | |
| `modalField`, `groupIDField`, `groupNameField` | `PBPopupPage` | |
| `popupReferencesField`, `hasReferencesField` | `PBPopupPage` | back-pointers |
| `timeoutField` | `PBPopupPage` | UInt32, 0 on every seed popup; nothing reads it - §7 |
| `modalField` | `PBPopupPageReference` | the reference's **own** flag - see §5 |
| `popupIDField`, `groupIDField`, `popupNameField`, `groupNameField` | `PBPopupPageID` | on the reference control - see §6 |
| `popupPageGroupsField` | `PBProject` | the group registry |
| `defaultPageField` | `PBProject` | the start page, as a page's `idField` - see §7 |
| `enableOfflineField` | `PBProject` | the Offline Page shown or not - see §7 |
| `nameField`, `familyNameField`, `styleNameField`, `windowsFamilyNameField`, `windowsStyleNameField`, `embeddedFileNameField`, `filenameField`, `sizeField`, `dataField`, `mIsDefault` | `PBFontResource` | a face: `dataField` its bytes, `sizeField` the size the project declares, which is not always theirs, `mIsDefault` set on a face GUI Designer supplies (Arial Black). A clone of the project's first, every field set from a project that carries the face, builds and is declared (`seeds/README.md`) |

## 5. Modal vs standard popups

A clean split, and it drives everything about references:

| | Modal | Standard |
|---|---|---|
| Size | the screen | its own, never the screen |
| Group | always ungrouped (0) | in a group - or ungrouped, shown by a reference bound to it by ID |
| Placement | invoked directly; references auto-created by Build | placed by a popup page reference bound to its **group**, or to the popup itself |

Cloning a modal popup as the target of a hand-authored reference is a dead end.

Measured over the 47 corpus projects' built `layout.json`, Offline Pages
aside: all 454 modals are the screen and none of the 442 standard popups is.
431 standard popups are in a group. The other 11 are ungrouped: nine seeds'
Volume Level - the Afterburn, Mach, Shockwave and Turbulence 525s, Mach's and
Shockwave's 535s, and the 300Ms - each placed by references bound to it alone,
`PopupPageID.PopupID` its own ID with `IsPopupPageIdValid` true and `GroupID` 0,
and an unreferenced `Popup Page1` in two of the client's archived projects.

A spec authors both kinds: a `popup_ref` names its `group`, or the one `popup`
it shows, which is then a standard popup in no group (`gdl.spec check`), and
the applier writes the binding the seeds' Volume Level has (§6). Built on GUI
Designer 1.28.0.7 from the Mach 1035 seed, which places no popup so, a strip
shown by such a reference on each of two pages, beside a group reference on
the first: in `layout.json` both references are `IsPopupPageIdValid` with the
built popup's `ID` and `PopupName`, `GroupID` 0 and `IsPopupGroupIdValid`
false, and the popup is in no group with `HasReferences` true - the seeds'
reading exactly (`archive/job-e823df9b/spec-22/`).

**Build draws a modal's page at the modal's own `transparencyField`** over the
page beneath: black, and its background image if it has one, but not its
background color - a spec modal with a `#242634` background built black. All
460 modals built in the corpus and the archived builds here are authored with a
black background and fill. 456 are at 35%, and their artwork is
`(0, 0, 0, 166)` throughout. The other 4 are at 0 - the Incoming ATC and VTC
modals of the client's two archived projects - and build opaque, hiding the
page beneath; both projects' `Booting` modal, at 35, draws its photo at alpha
166. So 166 is the templates' authored 35%, not a constant, and a clone keeps
its donor modal's: `gdl.spec` plans 35 on every modal, as every Design canvas
draws a modal (the profiles' `scrim`), and `tests/verify_built.py` reads it back
off the artwork.

To author a modal, clone a **modal** donor
popup, empty its `popupReferencesField` and set `hasReferencesField` false - the
donor's back-pointers name references that belong to the donor - and let Build
write the new popup's references. Flipping `modalField` on a standard clone is
untested.

**A modal's button can show another modal.** A modal carries no reference of
its own - every one Build writes is on a page, and no seed's built popup
holds one - so a modal shown from a modal is shown over whatever
page is up, through that page's reference to it. Built on GUI Designer 1.28.0.7 from the Mach 320 seed:
the round-three Mach room's Help, too deep for the 320, laid out as two modals,
`Help` with a Next button and `Help 2` with a Previous, each `nav` the other
(`docs/claude-design.md` §4). Both built as full-screen modals in no group,
`HasReferences` true, and every one of the panel's 11 pages came back with a
full-canvas reference to each of its four modals, in the popups' order -
`Help 2`'s above `Help`'s. So the program shows either over any page, and
hides the one it leaves: shown without that, a modal whose reference is lower
comes up under the one still showing. `tests/verify_built.py` and the ID map's
gate passed (`archive/job-e823df9b/small-panels/modal-mach/`).

**A reference control carries its own `modalField`**, separate from the popup's.
It is `True` on the references Build generates for modal popups - 126 of the
Afterburn 1035 seed's 131 references - and `False` on a group reference. A
clone inherits it, and Build **discards** an authored group reference that says
`True`, as one of its own, on the next build: the file builds with 0 errors and
the reference is simply gone. The client donor hides this because its
first reference happens to be a group reference; every seed exposes it. An
authored reference must be written `False`.

## 6. Popup bindings live in four places

Every one of these must agree. **Each mismatch fails silently** — the file
opens and builds, the binding just reads "Unassigned" in the UI:

1. the reference control's `PopupPageID` (`popupIDField` / `groupIDField`)
2. the popup's `groupIDField` **and** `groupNameField`
3. the popup's `popupReferencesField` — a `List<PBPopupReference>` of
   `{projectIDField, pageIDField, popupPageIDField, objectIDField,
   objectTypeField}` back-pointers — plus `hasReferencesField`
4. `PBProject.popupPageGroupsField`, the group registry: a
   `List<PBControlGroup>` of `{nameField, idField, referenceCountField}`.
   **An unregistered group id renders as "Unassigned."** The count is not a
   fifth place: Build keeps whatever it holds and builds the same panel (§7).

A generator should assert all four agree rather than trusting the writes.

A reference bound to **one popup** - the seeds' Volume Level (§5) - is the same
places with no group: its `popupIDField` the popup's `idField`, `groupIDField`
0 and `popupNameField` the popup's name; the popup's `groupIDField` 0 and
`groupNameField` empty; back-pointers shaped as a group reference's; and no
registry entry. `IsPopupPageIdValid` and `IsPopupGroupIdValid` are not fields:
read off 1.28.0.7's IL, they are `PopupID != UInt64.MaxValue` and `GroupID >
0`, so the two ids are the binding. `Test-GdlPopupBinding` checks either kind.

## 7. Gotchas

- PowerShell **unrolls a single-element list** returned from a function. Use
  `return ,$x`, or a `List<T>` reads back as a bare element and misleads you.
- `$HOME` and `$PID` are reserved PowerShell variables.
- `referenceCountField` reaches nothing Build makes. The client project stores
  46 / 8 / 13 / 2 against groups of 11 / 1 / 2 / 2 popups. Groups of 1, 3 and 5
  popups built at the applier's constant 2, rewritten to 46, 0 and 1 and built
  again, kept each value, and the second build's `layout.json` and artwork were
  the first's (`docs/from-scratch.md` §5, question 6). Any value builds the
  same panel.
- Cloned controls keep the source's `UserId` and per-page `ID`. Duplicate IDs
  are legal (Extron uses them for feedback mirrors) but allocate fresh ones
  unless a mirror is what you want.
- **Page and popup names must be unique across the whole project**, in one
  shared namespace — a popup may not take a page's name. Build fails with
  *"Duplicate page or popup page names are not allowed within the same
  project."* It is a **build** error, not a load error: the file opens fine and
  shows both duplicates in the tree. The name is the only identity that matters
  here; the `2210 - ` prefix on Extron's own names is a convention, not a field
  (`PBPage` has no page number), and duplicate numeric `idField`s draw no
  complaint at all.
- **A control outside its page's bounds is relocated to 0,0 by Build** —
  silently, with the build still reporting 0 errors. Width and height are left
  alone, so it reads as a positioning bug rather than as clipping, and nothing
  in the file records that it happened. This bites cloned popups hardest,
  because a clone keeps the **donor's** `widthField`/`heightField`: author the
  popup's own size before adding controls to it.
- **Build adds one full-canvas `PBPopupPageReference` per modal popup to every
  page — the Offline Page included only when `EnableOfflinePage` is on.** A
  generated page therefore comes back with more controls than were authored:
  one for each modal popup still in the project - the spec's own, since the
  applier drops the donor's (`docs/from-scratch.md` §5c), and every one of the
  donor's too under `keep_donor_pages`. It is not contamination from the
  clone; the donor's own pages carry the same references. `tests/audit_corpus.py`
  checks the rule against every built project it can reach, the few seeds with
  the Offline Page on among them - each references it too.
- **The Offline Page is GUI Designer's own popup, id 65535**, which every seed
  has, and `PBProject.enableOfflineField` shows it or not (`EnableOfflinePage`
  in `layout.json`; `OfflinePageID` is a property returning the constant). The
  seeds ship the switch both ways - every Turbulence seed on, every Mach seed
  off, Shockwave's and Afterburn's some of each - and Build follows it: with it
  off the page builds with no artwork (`TLPImageID` -1), `HasReferences` false
  and no reference on any page; on, with an asset and a full-canvas reference on
  every page. It is a modal over a shape, saying *It looks like this touchpanel has
  lost connection with the controller.* and *Please re-establish connection or
  call XXX.XXX.XXXX immediately for assistance.* - in one label (Afterburn's,
  Shockwave's, Mach's hubs and small panels, Turbulence's 525 and 320), or two
  placed apart, the second's text opening on two newlines (Mach's and
  Turbulence's other seeds); the Zoom Rooms seeds draw a page of their own. A
  spec's `offline` writes the switch and replaces words on the page, which the
  applier keeps whole, so its layout, type and colors stay the seed's. Built
  from the Mach 1035 seed (off, two labels) switched on with both labels' words
  replaced, `layout.json` read `EnableOfflinePage` true, a reference to 65535 on
  both pages and the new words on each label, and the page had its asset
  (`archive/job-e823df9b/spec-22/`). `tests/verify_built.py` holds all three to
  the plan.
- **A popup's `timeoutField` reaches no panel.** `PBPopupPage` serializes a
  UInt32 `timeoutField`, 0 on every seed popup, and no code in GUI Designer
  1.28.0.7 reads or writes it: no property wraps it, so the property grid never
  shows it (feature-flag mode's hidden properties included), and it is no
  `DataMember`, so `layout.json` - what the panel loads - has no timeout for
  any popup. Scanned, the IL of all 41 assemblies the bridge loads touches only
  a field of that name on the legacy `PanelBuilder.PBPopupPage`, whose
  `Timeout` property the grid edited as a byte. A spec's
  `timeout` is written by the applier, and Save and Build keeps it: built from
  the Mach 1035 seed with 30 on a standard popup, 7 on a modal and 0 on a
  third, the built project held 30, 7 and 0, and no member of the payload
  carried a timeout - its only matches were the probe's own words, its file,
  page and popup names and a caption (`archive/job-e823df9b/spec-22/`). `tests/verify_built.py` holds the
  built project's field to the plan, which is all a build can show: what a
  panel does with a popup that should hide by itself is the control program's
  to do, and `gdl.spec check` says so.
- **A built seed does not name the series template it came from.** A `.glt` is a
  `PBTemplate`: `mSeries`, its resolution and DPI, and the pages. `mSeries` is
  GUI Designer's `TLPSeries`, stored as its number: 1 `Series1020`, 2
  `Series720`, 3 `Series520`, 4 `SeriesVTLPWeb`, 5 `SeriesVTLPiOS`, 6
  `SeriesTLI`, 7 `Series320`, 8 `Series1520`, 9 `Series1220`, 10 `Series1720`,
  12 `SeriesVTLPAndroid`, 13 `Series300`, 14 `Series1230`, 15 `Series535`, 16
  `Series835`, 17 `Series1035`, 18 `SeriesVTLPEcp`. An Afterburn, Mach,
  Shockwave or Turbulence file named `<Theme> NNN Series` stores the series of
  that number; the ZRTP files named 725 and 1025 store 1 and 9, the Teams Rooms
  and Zoom Rooms ones 4, the ECP ones 18, and no installed template stores 16
  or 17. The project the Create Wizard
  makes from one has none of that but the pages: its `nameField` is the theme, the
  application and a label per screen (`Afterburn All-inclusive 725` comes from the
  1020 series, `... 525` from the 520), and `layout.json` adds a platform and a
  screen size, no series and no DPI. The pages are the template's, with their ids,
  names, sizes and controls' rectangles, plus the popup references Build adds
  (above). Names and ids say the theme more than the series (Shockwave's 720,
  1020, 1220, 1520 and 1720 series share them; its 320 has pages of its own, and
  its 520 and 535 a subset); sizes separate series of different canvases; only
  the rectangles separate the 520 and the 720, both 800x480, which share no
  page.
  `tests/verify_seed.py` compares them with the series GUI Designer takes for the
  model - its own `PBTemplate.PlatformProTypeToSeries`, which
  `gdl.templates.template_for` matches for every model it answers on 1.28.0.7.
- **A page's `userIdField` does not survive Build.** A generated page authored
  with `userIdField` 1000 comes back from Build with `UserId` equal to its `ID`
  (51 on the client donor), and every donor page and popup has
  `ID == UserId`. So the control program addresses pages and popups by **name**;
  only a control's `userIdField` is a stable number.
- **The start page is `PBProject.defaultPageField`**, a page's `idField`, and the
  built `layout.json` reports it as `DefaultPage`. A generated panel keeps the
  donor's unless it is written: one built from the client donor booted
  into the client's `1000 - Home`.
- **Retargeting a project needs Extron's factory, not a constructor.**
  `[Activator]::CreateInstance` on a platform class gets the resolution right
  and leaves `partNumberField` null, and GUI Designer then titles the project
  `Unknown: file.gdl` however correct `platformField`, `platformTypeField` and
  `screenSizeField` are - it identifies a panel by **part number**. Use
  `PBTouchPanelPlatformPro.CreatePlatform(PBProject, PlatformProTypeEnum)`.
- **Which way up a project is lives in three fields:** its platform's
  `horizontalResolutionField` and `verticalResolutionField`, and the project's
  `screenSizeField`. Those are the project-level fields that differ between the
  two Afterburn 300M seeds, portrait and landscape; everything else that differs
  is content - names, dates, the pages' own sizes, the controls the two series
  templates draw. The platform also carries the `supportedResolutions` it may
  take, both ways up for the panels that rotate (`docs/design-rules.md` §1);
  `CreatePlatform` hands back the default way, so a turned retarget writes the
  resolution fields after it.
  `layout.json` reports the result as `Platform.Orientation`, 0 for the first
  supported resolution and 1 for the second. A retarget of the Afterburn 1035
  seed to a TLP1035M at 800x1280 builds with every page at 800x1280, the
  full-canvas modals too, and its 880x525 popups scaled to 550x840.
- **A popup's authored size is its real size** — and a retarget must resize
  `PopupPages` as well as `Pages`. Resizing only `Pages` leaves every scaled
  popup control overflowing the old canvas, and Build moves them all to 0,0 (297
  on the client project). The size follows the popup's kind: in all 47 corpus
  projects every modal is the screen (454) and no standard popup is (442) - the
  client project's 16 are 136x496, 900x530, 915x800 and 995x800, 10 of
  Afterburn 1035's are 880x525 - and the **built** `layout.json` reports each
  popup at its authored size. So resize each popup by the same factor as its own
  contents; forcing a standard popup to the screen size turns it into a
  full-screen page in the shipped file. The old screen is `screenSizeField`, not
  the largest control: 4 of the 47 projects have no control as big as the
  screen.
- **A caption lives in one of three places** and a control that uses one leaves
  the others empty: the control's `textField`, the first state's `textField`
  (where a button's normally is), or the first state's `ftextField` - GUI
  Designer's formatted text, which carries tab and CRLF layout markers inline
  (`"\t\tDevice\r\nComms"`). 23 controls against 336 in the client
  fixture. Formatted captions are **flattened into the artwork**, so they read
  as `''` in `layout.json`: their words are in the built project and their
  lines only in the asset (`docs/editing.md` has how both are checked) - and
  because their line breaks are hand-placed, a longer replacement wraps onto an
  unindented second line over the icon. Renaming one works; renaming one to
  something longer quietly ruins it.
- `statesField` is a `PBStates` **wrapper**, not the list. The `List<PBState>`
  hangs off its `mItems`. Reading `statesField` as a list yields nothing and
  looks like a control with no states.
- **`$states.Count` is not the number of states.** `PBStates` has no `Count`
  member at all (its only count-like members are `InternalStateCount` and
  `ExternalStateCount`, both the list's real count). PowerShell 5.1 answers
  **1** for `.Count` on any object that lacks one, so it reads 1 for a
  one-, two- or four-state button alike. The indexer is fine — `$sts[0]` and
  `$sts[1]` both return a `PBState` — so `for ($i = 0; $i -lt $states.Count;
  $i++)` visits state 0 and stops, and every "write to every state" loop in
  both appliers did exactly that. Use `mItems`, via `Get-GdlStates`. This one
  is invisible from the outside: `TLPDefaultStateID` is 0, so a button whose
  state 1 was never written renders correctly, verifies correctly, and only
  misbehaves once a control system switches it On.
- **A button renders from its state, and its states are what make it useful.**
  `nameField` on a `PBState` gives the state its name, and `('Off', 'On')`
  covers **3475 of 3668** buttons (94.7%) in the 13 seeds and the client
  project that `research/2026-09-10/statenames.py` measured, and 60% of the
  buttons with two or more states give them different fills and 68% different
  artwork (`states.py` there; §9 has the audit's current Off/On share) — Build
  assigns each state its own `TLPImageID` and rasterizes them separately, and
  dedupes identical ones to a single ID. A button whose states are identical
  is inert: the control system sets it On and nothing changes.
- **More than two states is ordinary, and a clone can gain or lose them.**
  Across the 23 seeds and six fixtures, 8463 buttons carry states: 185 have
  one, 8123 two, 50 three and 105 four.
  The multi-state idioms are `('Muted', 'Level 1', 'Level 2', 'Level 3')` (81),
  `('Unavailable', 'Ready', 'Connected')` (29), `('Off', 'On', 'State2',
  'State3')` (24) and the client's `('Off', 'On', 'On_1')` camera buttons
  (7). GUI Designer allows up to 256: `MaxAllowedStateCount` reads 256 on the
  project, the TLP Pro 1035 platform and the button. Every state's `idField`
  and `indexField` equal its position, on all 8463 buttons in the model.
  `mItems` is an ordinary `List<PBState>`, so the applier resizes it directly —
  a clone of the last state appended to grow, states removed from the end to
  trim — and renumbers. Built on GUI Designer 1.28.0.7 from the Afterburn 1035
  seed, a two-state donor grown to three and four states and trimmed to one
  opened, built, and came back with every state named, captioned and drawn as
  its own artwork. `PBStates.statusField` holds `PBState.StatusFlags`
  (`PreventAddState` 1, `PreventDelete` 2, `PreventReorder` 4, `PreventRename`
  8, `PreventTransitions` 0x10); it is 0 on every button in the corpus, and the
  applier refuses a donor with any flag set.
- **Every button shows a state while it is held.** The button's own
  `<TLPPressFeedbackStateID>` — exported as `TLPPressFeedbackStateID` — names
  it: On (1) on all 7992 Off/On buttons in the seeds and fixtures, the last
  state on Extron's four-state volume mute (3), 0 on a one-state button. It is always a valid index in the built corpus. A clone
  inherits its donor's, which may name a state the clone no longer has, so the
  applier sets it. Each `PBState` also carries its own
  `<TLPPressFeedbackStateID>`, which is `-1` on 16,881 of 17,001 states and
  is not the one that matters. Whether the panel shows it at all is the
  button's `<HidePressFeedback>` (and `<HideVisualFeedback>`,
  `<HideTextFeedback>` for its state looks and captions), exported under
  those names: `False` on all 8463 buttons in the seeds and fixtures, but a
  clone keeps its donor's, so the spec writes all three.
- A clean build proves the file is **acceptable**, not that it is **correct**.
  Two separate traps (`flattenText`, and the relocation above) produce a file
  that opens, builds and is wrong. Finish with `tests/verify_built.py`, which
  diffs the built `layout.json` against the plan that produced it.
- **A "Dynamic Image" is not a new object type.** 1.28 added the feature —
  images the control system can swap at runtime without redeploying — and it
  needs nothing new from this format. `ObjectTypeEnum` still has only `Image`
  and `Video`; what makes an image dynamic is that it carries an object ID, in
  the `TLPImageID` field that already lives on `PBControl` (and `IStateInfo`)
  for every control. So a clone-and-retarget round trip carries it across
  untouched, and no code here needed changing.

  There is no platform gate on it in the graph. Extron's release notes scope
  the feature to the TLP Pro x35 series, Extron Control for Web and the Extron
  Control Pro app; the bundled help spells the first of those out as 535 / 835 /
  1035 / 1535 Series and omits ECP, which is a UI-availability statement rather
  than a format constraint. Whether a given panel honours it at runtime is
  firmware, not something this file can tell you.
- **A clock's format is its `patternField`**, a .NET date pattern (`'MMMM d'`,
  `'h:mm tt'`); `PBDateTime` has no format enum. `textField` holds that pattern
  drawn for 28 September 1960 at midnight (`'September 28'`), and layout.json
  reports the two as `Pattern` and `Text`. A cloned clock keeps its donor's
  pattern: a "date" clock cloned from the Afterburn 1035 seed built as
  `September 28, 12:00 AM`.
- **A clock can be cloned from another project of the theme.** Shockwave's
  and Turbulence's 320 seeds carry no `PBDateTime`; their 525s do. A clock
  deep-cloned out of the 525's project into the 320's (`Apply-GdlPlan.ps1
  -TypeDonors`, which `gdl.spec donors` and `plan --donor` name by
  `gdl.seeds.carrier`, the theme's smallest seed with one), its pattern,
  font, size, color and alignment written as any clone's, built on GUI
  Designer 1.28.0.7 on each 320 as planned: `h:mm tt` as `12:00 AM` and
  `MMMM d, yyyy` as `September 28, 1960`, in the 320's own Open Sans
  resource, each with its artwork (`archive/job-e823df9b/small-panels/clock/`).
  What the applier does not write rides along from the other seed - its time
  zone (`Pacific Standard Time` in both themes' seeds) and its dynamic text -
  and a font reference naming the other project's resource is pointed at the
  project's own (`Set-GdlFont`). Only a clock crosses so (`gdl.spec
  CROSS_SEED_TYPES`): an image or a slider draws art its own seed's
  resources name, which no build has shown cloned across.
- **A slider's thumb is an image, and its fill a color.** The Afterburn
  seeds' volume slider has `sliderThumbTypeField` 2 and its thumb in
  `sliderThumbImageField` - `440x440_thumb-1-periwinkle_sel.png`, the scheme-1
  secondary accent, from the kit's `Sliders & Toggles` - and the filled part in
  `sliderFillColorField`, `#BABCCE`. Build draws the thumb as its own asset,
  `SliderIndicatorImageID`, so a clone under another scheme keeps the
  periwinkle thumb until the image is set. The art is stretched into that
  asset, not fitted and never turned: the Afterburn 1035 Portrait's 31 px
  sliders draw the square file 30x50, and a Shockwave slider lying right or
  left its 156x102 file 34x52 - `sliderThumbWidth` and `sliderThumbHeight`
  being literal on the page whichever way the slider lies.
- **A slider's rail can be images too, and a border hides them.** The
  Shockwave, Mach and Turbulence seeds' sliders draw the rail from the kit: the
  track shown empty in `backgroundImageField`, the fill shown full in
  `sliderFillImageField`. Build writes the two as `TLPMinValueImageID` and
  `TLPMaxValueImageID`, each stretched into `sliderTrackWidth` across and the
  slider's length less the thumb along, centered - inset half the thumb at
  each end, where its center stops: Mach's 8 px rail in a 30 px slider,
  Turbulence's 44 px striped one 26 px short of each end. The full asset is the
  fill drawn over the track - Shockwave's fill is narrower than its track, whose
  rim shows round it - and a track wider than its slider is still drawn
  `sliderTrackWidth` across, centered and cut to the control: a 47 px slider
  with a 52 px track. So drawn, every rail of the three themes' seeds reads 0%
  off its kit files (`rail_image` in `tests/verify_built.py`). The art is drawn
  standing up, and on a slider lying right or left Build turns it a quarter
  turn first, its top to the slider's full end - clockwise lying right,
  anticlockwise lying left - and lays it out the same way along the slider's
  width: Shockwave's, built so in the format probes, reads 0% off turned and
  45 to 82% laid on its side unturned (`examples/probes-128/`; no seed draws a
  horizontal rail from art, and none a slider whose orientation is `down`).
  Those sliders author no border and a Transparent fill; one with a border
  resource and a fill builds that bordered fill in place of the art, so a
  Shockwave slider planned with the rounded border and black fill builds an
  opaque black block with the right images on the model. The applier clears every clone's `backgroundImageField`
  - on a slider, its track - but an art-drawn level's (below), so the plan
  writes the rail and the verifier reads it back off the two assets.
- **A Level's `TLPImageID` is its full bar; a Slider's is its empty track.**
  Build writes both kinds' empty and full art as `TLPMinValueImageID` and
  `TLPMaxValueImageID`, and names one of them as the control's `TLPImageID`:
  the max on all 33 Levels in the seeds and fixtures, the min on all 206
  Sliders. So a Level's authored fill - its track - is on its min asset, and
  its `TLPImageID` reads back as the accent bar.
- **A Level is its rail, and its bar is a color or an image.** Build draws a
  Level over its whole box - it has no track width, unlike a slider - and every
  Afterburn seed's Level is 15 px across. `gaugeFillTypeField` says which bar:
  0, `gaugeFillColorField` - Afterburn's and Mach's seeds, Afterburn's
  `#626ACF` (scheme 1's secondary accent), so a clone keeps that under any
  other scheme until it is set; 1, `gaugeFillImageField` over the empty track
  in `backgroundImageField` - Shockwave's and Turbulence's, whose color is an
  unused `#0000FF` - which Build draws in place of any color. The applier
  clears every clone's background image, but a level its donor draws from art
  keeps it (the plan's `keep_art`, from `gdl.spec`'s donor check) and is
  planned no bar color, and the verifier holds its empty and full art apart.
- **A page's background image is a named `PBImageResource`**, referenced from
  `backgroundImageField` by a `PBResourceReferenceImage` and drawn by
  `backgroundImageLayoutField` over the page fill - the Afterburn seeds fit
  `6400x4000_bg1.png` over `#242634`, while every Mach 1035 page stretches its
  3:2 `mach-bg-02.png` over the 16:10 page (fitted, it builds with bands of fill
  down both sides). `ImageLayoutEnum` is `Fill` 0 (fit, keeping the aspect, as
  CSS `contain`), `Stretch` 1, `Tile` 2, `Native` 3, `Offset` 4; a spec page's
  `background_layout` is `fill` or `stretch`. Build rasterizes the two into
  the page's asset and layout.json does not name the image, so it is verified
  off that asset. An image the project lacks is appended by cloning an existing
  `PBImageResource` and setting its bitmap, name and size
  (`Add-GdlImageResource`).
- **An image control draws its art from `backgroundImageField`.** A
  `PBImage` has no states; every one in the Turbulence seeds names its art
  there, by a `PBResourceReferenceImage`, and lays it out by
  `backgroundImageLayoutField` at MiddleCenter with no offset: the header
  and footer bars (`2047x151_header.png`, `1648x134_footer.png`) Stretch over
  their box, a source popup's device picture (`1152x1152_<device>.png`) Fill
  in its own. Build's artwork of each, its `TLPImageID`, is the file so laid
  out - 0% off on every bar and device picture of the 1035, 725 and 525
  seeds, and the nearest other picture 10% off (`check_images` in
  `tests/verify_built.py`). The side bars are `PBImage`s with no art: a black
  fill at 85% transparency. A spec `image` control is one (`image`, `layout`
  `fill` or `stretch`); the applier sets its art after clearing the clone's,
  since the Turbulence seeds' first `PBImage`, a clone's donor, is a side bar
  laid out Native (3) - and black, which the applier's opaque clone would
  build under the art, so an image given no `fill` is written transparent
  and with no border, as every `PBImage` in the seeds has none. Only a seed with a `PBImage` can author one
  (`gdl.spec donors`): every Afterburn seed, Mach's tier A ones and
  Turbulence's but its 320 - no Shockwave seed, and none of Mach's hubs,
  320 or 300M.
- **A standard popup can carry a background image**, as a page does, in its
  own `backgroundImageField`. Shockwave's and Turbulence's hubs draw every
  standard popup on the page's photo, stretched to the popup:
  `seeds/Turbulence 525.gdl`'s 12 on `bkgd_swoop_plain.png`, Shockwave 525's
  and 535's 12 each on `800x480 bkgd.png`, each 702x480 - so a popup's photo
  is the page's squeezed, not the page's showing through. Build rasterizes it
  into the popup's asset with its fill, as a page's.
- **A donor's image of a kit file's name need not be that file.** The Shockwave
  1035 seed carries `960x440_yellow_sel.png` and `960x440_red_sel.png` whose
  pixels differ from the kit's files of those names in 67% of their pixels -
  they draw the resting look - so a Help button whose On state named the kit's
  `960x440_yellow_sel.png` built both states as one artwork. A name is reused
  only when the pixels agree (compared as 32-bit ARGB, since the resource and
  the file are encoded differently); otherwise the file goes in as
  `<name>_1`, GUI Designer's own spelling of a second copy.
- **A color can be a palette entry.** A `PBColor` with `paletteIndexField` >= 0
  is `PBProject.paletteField`'s entry at that index (`PBPaletteEntry`: 0
  Transparent, 1 Black, 9 White, ...) and its `valueField` is empty; Build
  draws the entry. Every color in the Afterburn 1035 seed is custom (-1), while
  the Mach 1035 seed has 126 palette colors and Shockwave 1035 107, mostly
  state captions. A clone of one keeps the index, so writing only the value
  changes nothing: Shockwave's lit captions are palette Black, and a clone
  rewritten to white built black. `Set-GdlColor` writes -1 with the value, and
  `gdl.project` reads an entry through the palette.
- **A color can be stored by name.** A `System.Drawing.Color` with `state` 1 is
  the `KnownColor` in `knownColor` - 27 Transparent, 35 Black, 105 LimeGreen,
  164 White - and its `value` is 0. Every seed stores colors so: Shockwave
  1035 211 White and 206 Black, Afterburn 300M 90 Black and 55 White, every
  Turbulence label White. `gdl.project` reads them through .NET Framework's own
  table of the web colors (`KNOWN_COLORS`) - Framework's, since it differs from
  CSS once (DarkSeaGreen `#8FBC8B`); reading only the value read each as no color.
  `Set-GdlColor` writes `Color.FromArgb`, which replaces the whole struct, so a
  named color never survives a write.
- **A control's `transparencyField` fades everything it draws** - a percent.
  28 of the Shockwave 1035 seed's 34 shapes are 0.0, the video well on each of
  its five Main pages 85.0 and its Offline Window 25.0. A clone keeps its
  donor's, and the seed's first shape is a well, so a panel cloned from it
  builds at 15% opacity with the right fill in every field. The spec says
  translucency with the fill's alpha, so the applier writes 0. A button's
  `PBState` carries a `transparencyField` of its own that fades that state the
  same way: one of the Mach 320 seed's 66 states is 30.0, and the buttons
  cloned from it built every fill at 70% of its alpha (180 as 126). The
  applier writes 0 there too.
- **A translucent fill reaches the artwork at its own alpha.** Build writes the
  alpha exactly and the color within premultiplying's rounding: Turbulence's
  rail, black at 38, built (0, 0, 0, 38) throughout, and its shade, #020D1A at
  128, built (1, 13, 25, 128). Each channel goes into premultiplied form
  rounded, (c * a + 127) // 255, and out truncated through a 16.16
  reciprocal, p * ((255 << 16) // a) >> 16 - twice for a fill, and a third
  time inside the rect of an image drawn over it; that reproduces every
  translucent fill in Mach's call builds and its 1035, 725 and 525 seeds, 26
  looks at nine alphas. A channel comes back up to 255 // alpha + 1 off bare
  and one more under an image, high as well as low: Mach's Make Call, #659945
  at 220, built (99, 151, 69, 220) bare and (98, 150, 69, 220) under its
  755x440 call icon, but for the last column and row, past the fitted icon -
  as the Mach 1035 seed's own Initiate Call is built, byte for byte - and the
  seed's VC Call, #86D161 at 80 under its icon, green 210. GUI Designer's
  snapshots, and the compositor, draw such a pixel at full strength
  (`docs/render-fidelity.md` §2), but the theme is drawn for a panel that
  blends it - the Turbulence seed's own header and footer art is alpha 128
  throughout. `tests/verify_built.py` reads a translucent fill off the pixels
  at its alpha, as it reads an opaque one off the opaque pixels, within that
  rounding (`_fill_tolerance`).
- **A built-in border draws as its project defines it.** Every project carries
  its own copy of GUI Designer's 13 built-ins, each a `PBBorderInfo` in its
  resource's `dataField` - `cornerRadiusField`, `thicknessField` - and seeds
  differ (`Project.border_geometry`): 2D Rounded Rectangle is radius 1 and
  thickness 0 in the Mach 1035 and 525, 2 and 1 in the Shockwave 1035, 10 and 3
  in the Turbulence and Afterburn ones; 2D Rectangle is thickness 3 in the
  Mach 1035 and 0 in its 525. Build draws exactly that. On the Mach 1035 a button
  on 2D Rounded Rectangle whose Warming Up state was Off's fill with an accent
  `borderColorField` built as Off's very artwork, its Cooling Down's white
  outline was not drawn either, and its corners came out square - a 460 x 100
  button's corner pixel at alpha 96 of the fill's 180. On the clean-room
  panel's 2D Capsule, thickness 3, the stroke is three pixels of `muted` inside
  the edge. `BORDER_GEOMETRY` is the client fixture's and only the preview's.
  So `gdl.spec donors`, and the translator with the panel's own seed, name a
  stroke on a border the seed gives no thickness (`Panel.stroke_rules`), and
  each design system draws a built-in as its design panel's seed defines it.
  Mach's ghost, solid and highlight buttons stay on 2D Rounded Rectangle, as
  554 of the seed's 662 button states are - square, their states told apart by
  fill. `Mach - 10 Radius 2 Thick`, on 16 of them, builds rounded: the same
  button on it has its corner and (3, 3) empty and (6, 6) fill.
- **A kit image button carries its image on each state, not on the control.**
  Every image button in the Afterburn 1035 and 1535 seeds has an empty
  control-level `buttonImageField` and one per state, drawn `Fill` and
  `MiddleCenter`, with a border reference whose resource name is empty - the
  kit's image is the whole button, selection line included. Its caption is
  placed by the caption itself: two CRLFs put a source's label under the icon,
  leading spaces put a list button's past it (a formatted-text caption in the
  seed, which Build bakes into the artwork; a plain one is drawn live). Build
  rasterizes image, fill and border into the state's artwork, and layout.json
  does not name the image, so it is verified off that artwork.
- **`ApplicationBuildVersionInfo` in the built `layout.json` lags one build
  behind on a project carried across versions.** Open a 1.27-authored project in
  1.28 and Save and Build: the `ProjectGCP` is restamped immediately
  (`GUI Designer 1.28.0.7`, `Extron.GUICPro.Layout.Contracts 5.6.0.0`) but the
  payload still reports `1.27.0.9`, because that first build reuses the cached
  payload. The second build regenerates it. `gdl/data.py` surfaces this as
  `'app'`, so do not treat it as "which version built this".
